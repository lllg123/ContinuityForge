# 约束差距审计与 RCPSP 子集定义（M0）

审计日期：2026-10-23。依据当前 `scheduling/`、`adapters/`、`benchmark/`、`web/`、三个示例、测试、[算法设计](algorithm-design.md)、[接口说明](scheduling-interface.md)和[基准报告](benchmark-report.md)。本文件是**实施前差距与架构计划**；“目标”列不是已实现能力。代码与数据集来源必须在后续阶段逐项验证。

## 项目定位与严格范围

目标是 **MoonBit 单模式、非抢占、整数时间的可再生资源受限项目调度库**。每个任务 `i` 固定时长 `dᵢ`，有前置 DAG，可能同时需求多个资源 `r` 的非负整数数量 `qᵢᵣ`；每种资源有正整数容量 `Cᵣ`，任意时刻 `t` 满足 `Σ_{i:sᵢ≤t<fᵢ} qᵢᵣ ≤ Cᵣ`。任务占用半开区间 `[sᵢ,fᵢ)`；`fᵢ=sᵢ+dᵢ`，前置 `j→i` 要求 `sᵢ≥fⱼ`，最早开始 `sᵢ≥releaseᵢ`，硬截止 `fᵢ≤deadlineᵢ`，可选总目标 `maxᵢ fᵢ≤T`。首要优化目标为最小化 makespan。时间、需求及累计量必须防止有符号 32 位整数溢出。真实任务时长为正；为无损读取 PSPLIB，v2 可明确支持零时长、零资源需求的虚拟起止里程碑。

本轮**不支持**多执行模式、非可再生/可消耗资源、替代资源选择、日历/休息期、抢占、准备时间、随机时长、动态到达后重新调度、成本目标或全部工业调度问题。`priority` 仅用于启发式平局，不改变可行性。RTO/RPO 是业务目标与数据恢复指标，不自动等于每项任务的 `deadline`。PSPLIB 的单模式 RCPSP 实例应保持原始资源、时长、零时长虚拟节点与前置关系；超出本子集的实例必须排除并记录，不能删约束后仍引用原最优值。

## 约束能力矩阵

| 约束/指标与数学定义 | 当前状态与证据 | 目标模型、独立校验和求解路径 | 必要测试与公开基准 |
| --- | --- | --- | --- |
| 非抢占、固定时长：`fᵢ=sᵢ+dᵢ` | 已支持正时长、单段执行；`Task`/`ScheduleEntry` 与 `validate_schedule` 校验。 | v2 使用固定整数时长；仅虚拟里程碑可为零；拒绝时间溢出。串行排程一次安排完整区间。 | 正/零/负时长、`Int` 上界、半开端点；PSPLIB `.sm` 的虚拟节点。 |
| DAG 前置：`sᵢ≥fⱼ` | 已支持且检查环、缺失和重复边；根包恢复适配器复用调度包。 | v2 保持有向边语义；候选与外部导入解均调用同一独立验证器。 | 链、菱形、环、缺失边、同一时刻完成后启动；PSPLIB 前置表。 |
| 可再生资源容量：`Σactive qᵢᵣ≤Cᵣ` | **缺失**；目前 `Resource` 只有 ID、容量恒为 1，重叠即拒绝。 | 新增 `capacity` 与逐任务 `demand`；验证器用事件扫描，结束事件先于同刻开始事件；求解器找所有资源同时可行的最早区间。 | 容量 4、需求 2+1 可并行而 2+3 不可并行；容量/需求边界及累计溢出；PSPLIB J30。 |
| 多资源同时占用：一个任务跨所有 `r` 使用同一 `[sᵢ,fᵢ)` | **缺失**；`Task.resource_id` 只有一个资源。 | v2 保存需求向量，禁止拆分任务；验证器逐资源复核，求解器联合检查所有需求。 | CPU+内存同时占用、单资源空闲但另一资源满载；PSPLIB `.sm` 多列需求。 |
| 最早开始：`sᵢ≥releaseᵢ` | **缺失**；解码从 0 或前置完成时刻起。 | v2 `release_time` 非负；解码起点取 `max(release, predecessors finish)`。 | 释放前开始拒绝、释放时开始接受；自建场景。经典 PSPLIB J30 没有此字段，不能据此验证本项。 |
| 硬截止：`fᵢ≤deadlineᵢ` | **缺失**；现有 `target_makespan` 只约束整体完工。 | v2 `deadline` 可选；验证器拒绝超时。无可行排程时区分“求解器未找到”与已证明不可行。 | 截止时完成接受、超过拒绝、不可达下界；自建场景，不能把 `due_date` 惩罚当作硬约束。 |
| 总目标：`Cmax≤T` | 已支持校验；旧适配器为保留超标计划，会先用无目标问题排程再报告 `target_met`。 | v2 可分别返回候选工期与目标达成状态；硬目标校验须拒绝超标外部排程，状态语义清晰。 | 恰好达标/超标/空任务；PSPLIB 经典目标是最小化工期，原实例没有目标值。 |
| 任务完整性/资源合法性 | 已检查任务数、重复、未知资源、时长；错误主要是字符串。 | 增加结构化违规报告：类别、任务、资源、区间、实际/上限；所有算法与导入解共用。 | 缺项、重复项、未知资源、需求超容量、可变公开数组再校验。 |
| 最优性状态/下界 | `exact_reference` 仅 ≤8 项且搜索完整才证明；旧 `OptimizationReport.lower_bound` 是路径/独占负载下界。 | v2 保留合法下界与求解状态；成熟求解器比较须区分 OPTIMAL、FEASIBLE、INFEASIBLE、UNKNOWN，未证明最优时不报精确最优差距。 | 小例精确对照、时间上限、无解/未知；PSPLIB 官方 OPT/LB/HRS 分开记录。 |
| 版本化交换格式 | Web `schema.v1.json` 只含单资源字段，不是通用库输入输出契约。 | 新建 v2 问题/排程 Schema，明确资源容量、需求、时窗、状态、界和诊断；v1 显式迁移为容量 1、需求 1。 | v1 兼容样例、v2 往返、非法版本/字段；公开实例的规范化 JSON。 |

## 现有实现与差距的具体位置

- `scheduling/model.mbt` 和 `interfaces.mbt` 固定单独占资源；`validate_schedule` 用成对区间重叠检查容量 1，没有容量累计事件扫描或结构化报告。
- `baselines.mbt` 的 `earliest_slot` 只检查 `task.resource_id`，`optimization.mbt` 的资源负载下界把该资源所有任务时长相加；两者不能直接用于容量 >1 或多资源需求。旧局部搜索确实验证最终候选，但在新模型上必须重建解码与下界。
- `adapters/recovery`、`adapters/pipeline` 和 `web/engine` 都调用旧通用调度核心；`web/scenarios/schema.v1.json` 不含容量、需求或时窗。旧 API、浏览器数据与示例须保持原语义，并显式引入 v2 路径。
- `benchmark/runner` 的六组输入完全由固定种子生成；已有三基线、预算搜索、精确小例、消融与 CSV/SVG，但没有公开实例、成熟求解器或统一模型比较。旧报告只适用于旧约束模型，不可混入 v2 指标。

## 成熟实现与公开基准对照

- [PyJobShop 项目调度示例](https://pyjobshop.org/stable/examples/project_scheduling.html)定义单模式 RCPSP 的可再生容量、任务需求、多资源及工期目标，并另列多模式扩展。本项目仅取前者的固定模式子集，不复制其源码。
- [OR-Tools 官方 RCPSP CP-SAT 示例](https://github.com/google/or-tools/blob/stable/examples/python/rcpsp_sat.py)使用任务区间、前置约束和累计资源约束，适合作为独立实验基线。M4 要用同一规范化实例单独写等价模型、记录求解状态与界，而不是把 CP-SAT 当作 MoonBit 核心。
- [PSPLIB 官方单模式数据页](https://www.om-db.wi.tum.de/psplib/getdata.php?mode=sm)明确区分 HRS（最好已知可行解）、LB（已证明下界）和 OPT（已证明最优）；J30 共 480 个已证明最优实例。M5 应从小的 J30 子集起步，记录原始文件名、下载链接、校验和、转换规则及纳入/排除清单。数据再分发许可尚未核实；核实前只提供官方下载说明与转换程序，不将整库直接提交。

## 分阶段架构计划与兼容性门槛

1. **M1–M2：** 在 `scheduling/` 增加 v2 类型和验证器，不修改现有公开记录字段或旧 `Task::new` 签名。旧单资源任务可显式映射为 `capacity=1, demand=1, release=0, deadline=None`。v2 验证器独立于求解器，并先固定反例测试。
2. **M3：** 为 v2 实现联合资源最早可行区间解码和四种算法；候选结果必须经 v2 验证器。旧 API 继续用于旧 Web 与恢复流程，行为差异在迁移文档中逐项说明。
3. **M4–M6：** 规范化 JSON 同时输入 MoonBit 与固定版本 Python OR-Tools；加入官方 J30 单模式子集，复现原始与失败结果，分开报告已证明最优、可行和未知。旧合成基准作为回归集保留。
4. **M7–M9：** 固定 v2 API 与 Schema，新增完整 CI、恢复及通用场景，更新 Web/README/许可证与 CI。只有约束矩阵、外部基准和三个场景实际通过后，才宣称新定位的验收完成。

每阶段完成后更新[实施进度](IMPLEMENTATION_PROGRESS.md)和对应独立提交；不得将此计划当作已完成功能。
